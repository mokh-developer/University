# UNI-02: موردکاربردی ثبت دانشجو

**وضعیت:** پیش‌نویس برای بررسی مالک محصول  
**اندازه:** کوچک (S)  
**بخش:** `student`  
**پیش‌نیاز:** ادغام تسک `UNI-01` در شاخهٔ `main`

## هدف

فراهم‌کردن مسیر کاربردی ثبت دانشجو در لایهٔ Application، با تکیه بر مدل دامنهٔ `Student` و بدون وابستگی به HTTP یا پایگاه داده. این موردکاربردی از طریق یک Port خروجی ذخیره‌سازی را درخواست می‌کند؛ آداپتر واقعی در تسک جداگانه ساخته می‌شود.

## شرح تسک

به‌عنوان مسئول ثبت اطلاعات دانشجویان، می‌خواهم اطلاعات پایهٔ دانشجو را به موردکاربردی ثبت بدهم تا دانشجو با قواعد دامنه ایجاد و برای ذخیره‌سازی ارسال شود و شناسهٔ او به من برگردد.

## محدودهٔ کار

- ایجاد ساختار لایهٔ Application زیر feature دانشجو، برای نمونه:

  ```text
  com.b.university.student.application
    port.in
    port.out
    service
  ```

- تعریف ورودی موردکاربردی `RegisterStudentUseCase` با ورودی شامل شمارهٔ دانشجویی، نام و نام خانوادگی.
- تعریف Port خروجی `StudentRepository` با عملیات لازم برای بررسی وجود شمارهٔ دانشجویی و ذخیرهٔ `Student`.
- پیاده‌سازی موردکاربردی ثبت دانشجو در یک سرویس Application:
  1. ساخت دانشجو با `Student.register(...)` تا قواعد و نرمال‌سازی دامنه اعمال شود.
  2. بررسی شمارهٔ دانشجویی نرمال‌شده از طریق Port مخزن.
  3. در صورت تکراری‌بودن شماره، رد ثبت با استثنای مشخص و بدون ذخیره.
  4. در غیر این صورت، درخواست ذخیره از مخزن و بازگرداندن `StudentId`.
- افزودن تست واحد برای موفقیت، تکراری‌بودن شماره، ورودی نامعتبر و عدم ذخیره در حالت خطا.

## قرارداد پیشنهادی

جزئیات نام‌گذاری و نوع‌ها را با سبک موجود پروژه هماهنگ کنید؛ قرارداد باید معادل این رفتار را فراهم کند:

- ورودی: `studentNumber`, `firstName`, `lastName`
- خروجی موفق: `StudentId`
- Port مخزن:
  - `existsByStudentNumber(String studentNumber)`
  - `save(Student student)`
- خطای تکراری: استثنای مشخصی مانند `StudentNumberAlreadyExistsException`

از برگرداندن Entity پایگاه داده یا نوع‌های HTTP در قرارداد Application استفاده نکنید.

## قواعد و رفتار مورد انتظار

- اعتبارسنجی فیلدها و حذف فاصله‌های ابتدا و انتها بر عهدهٔ مدل دامنهٔ `Student` است؛ قواعد را در Application تکرار نکنید.
- بررسی تکراری‌بودن باید با شمارهٔ دانشجویی نرمال‌شده انجام شود.
- اگر ورودی دامنه نامعتبر باشد، خطای دامنه به بیرون منتشر شود و مخزن برای بررسی یا ذخیره فراخوانی نشود.
- اگر شماره تکراری باشد، خطای مشخص تکراری‌بودن برگردد و `save` فراخوانی نشود.
- در موفقیت، `save` دقیقاً یک بار فراخوانی و شناسهٔ همان دانشجوی ساخته‌شده برگردانده شود.
- Application فقط از Domain و abstractionهای Port استفاده کند؛ به Spring MVC، JPA، PostgreSQL یا Servlet وابسته نباشد.

## خارج از محدوده

- Controller، REST API، JSON، status code و مدیریت خطای HTTP.
- آداپتر واقعی PostgreSQL/JPA، Entity پایگاه داده، migration و تراکنش.
- پیکربندی Spring برای اتصال و ساخت Beanها.
- احراز هویت، نقش‌ها، ثبت رخداد و امکانات دیگر دانشجو.
- تضمین نهایی یکتایی در برابر درخواست‌های هم‌زمان؛ آداپتر و قید یکتای دیتابیس در تسک persistence باید آن را تضمین کنند.

## معیارهای پذیرش

- موردکاربردی ثبت در feature `student` و لایهٔ Application قرار دارد.
- موردکاربردی از طریق Port خروجی با مخزن ارتباط می‌گیرد و به پیاده‌سازی ذخیره‌سازی وابسته نیست.
- ثبت معتبر، دانشجو را با مدل دامنه می‌سازد، ذخیره‌سازی را یک بار درخواست می‌کند و `StudentId` را برمی‌گرداند.
- شمارهٔ دانشجویی پس از نرمال‌سازی دامنه برای بررسی تکراری‌بودن استفاده می‌شود.
- شمارهٔ تکراری با خطای مشخص رد می‌شود و ذخیره انجام نمی‌شود.
- ورودی نامعتبر پیش از هر تعامل با مخزن رد می‌شود.
- تست‌ها با مخزن جعلی یا mock اجرا می‌شوند و به PostgreSQL یا بالا آمدن Spring context نیاز ندارند.
- هیچ Controller، کد JPA یا پیکربندی پایگاه داده به این تغییر اضافه نشده است.

## راهنمای اجرای تسک

1. ابتدا مطمئن شوید `UNI-01` در `main` ادغام شده است؛ شاخهٔ تسک جدید را از آخرین `main` بسازید.
2. شاخه را با الگوی زیر نام‌گذاری کنید:

   ```text
   feature/UNI-02-register-student
   ```

3. موردکاربردی، Portها و تست‌های واحد آن را پیاده کنید.
4. تست‌ها را اجرا کنید:

   ```powershell
   .\mvnw.cmd -Dtest=StudentTest test
   .\mvnw.cmd test
   ```

   اگر تست عمومی برنامه در این مرحله به تنظیم دیتابیس نیاز دارد، نتیجه و علت را در PR شفاف بنویسید؛ تست واحد موردکاربردی نباید به دیتابیس نیاز داشته باشد.

5. تغییرات را مرور کنید و فقط فایل‌های مربوط به این تسک را commit کنید. پیام پیشنهادی:

   ```text
   feat: add student registration use case
   ```

## ساخت Pull Request

بعد از commit، شاخهٔ تسک را push کنید؛ `main` را مستقیم push یا محلی با شاخهٔ تسک merge نکنید:

```bash
git push -u origin feature/UNI-02-register-student
```

سپس در GitHub:

1. مخزن `mokh-developer/University` را باز کنید و **Compare & pull request** را انتخاب کنید؛ اگر پیشنهاد نمایش داده نشد، از بخش **Pull requests → New pull request** استفاده کنید.
2. مقصد (**base**) را `main` و شاخهٔ تغییر (**compare**) را `feature/UNI-02-register-student` انتخاب کنید.
3. عنوانی روشن وارد کنید، مانند `feat: add student registration use case`.
4. توضیحات PR را با هدف تغییر، طراحی Portها، رفتار شمارهٔ تکراری و دستور/نتیجهٔ تست‌ها کامل کنید. اگر بخشی انجام نشده یا محدودیتی وجود دارد، همان‌جا ذکر کنید.
5. قبل از ساخت PR، فهرست فایل‌ها و اختلاف‌ها را بررسی کنید تا فقط تغییرات `UNI-02` در PR باشد. اگر کامیت نامرتبطی در مقایسه با `main` دیده می‌شود، PR را نسازید و ابتدا با مدیر پروژه هماهنگ کنید.
6. PR را برای بازبینی ارسال کنید و به نظرهای بازبین پاسخ دهید. پس از تأیید مدیر/بازبین، ادغام طبق روش تعیین‌شدهٔ مخزن انجام می‌شود؛ تا آن زمان شاخهٔ `main` را تغییر ندهید.
